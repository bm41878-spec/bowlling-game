[P0] GameManager vs GameStateManager 책임 중복
--------------------------------------------------------------------------------
   위치: Assets/Scripts/Core/GameManager.cs, GameStateManager.cs
   문제:
     - GameManager.OnThrowComplete()가 상태 전이를 직접 호출하려 하지만,
       실제 상태 전이는 GameStateManager.ChangeState()가 담당.
     - GameManager의 거의 모든 메서드가 NotImplementedException 상태이며,
       두 클래스 간 협력 경계가 정의되지 않음.
     - 현재 GameStateManager가 Ready, Scoring 등의 흐름을 임시로 담고 있어
       역할 분담을 명확히 하지 않으면 통합 시 충돌 가능.
   개선:
     - GameManager = 프레임/투구/점수 등 도메인 로직 (turn manager)
     - GameStateManager = FSM 전환 책임만 (transitions)
     - GameManager가 GameStateManager.ChangeState()를 호출하는 단방향 의존
       구조로 정리.

[P1] Singleton 패턴 남용 + 초기화 순서 위험
--------------------------------------------------------------------------------
   위치: GameStateManager, InputController (Instance 정적 참조)
        BallAimer.Start(), BowlingBall.Start(), PowerGaugeUI.Start()
   문제:
     - Awake()에서 Instance 등록, Start()에서 Instance 참조 → Unity가 보장하는
       순서이긴 하지만 Script Execution Order가 설정되어 있지 않음.
     - GameStateManager.Instance가 null인 상태에서 다른 컴포넌트가 참조하면
       NullReferenceException 발생 가능.
     - 단위 테스트 작성 시 Singleton은 격리가 어려움.
   개선:
     - Script Execution Order에서 InputController, GameStateManager를
       기본값(-100 등)으로 우선 실행되도록 설정.
     - 장기적으로는 ServiceLocator 또는 의존성 주입(VContainer/Zenject) 도입.

[P2] FindFirstObjectByType, GameObject.Find 사용
--------------------------------------------------------------------------------
   위치:
     - BowlingBall.Start(): FindFirstObjectByType<PowerGaugeUI>
     - BowlingBall.HandleStateChanged(): GameObject.Find("BallSpawnPoint")
       (상태 전이마다 매번 호출)
   문제:
     - 매 상태 전이마다 GameObject.Find 호출 → 씬에서 전체 검색은 O(N) 비용.
     - 문자열 기반 참조는 리네임에 취약(컴파일러 검증 불가).
   개선:
     - [SerializeField] Transform ballSpawnPoint; 형태로 Inspector 참조.
     - PowerGaugeUI도 Inspector 노출 또는 GameManager에서 주입.

--------------------------------------------------------------------------------

     - BallAimer: laneHalfWidth = 0.43f, ballStartZ = 0.5f
     - BowlingBall: IsInGutter 판정 0.533f, minForce/maxForce 8~18

     - 레인 너비, 거터 경계가 클래스마다 다른 값으로 흩어져 있음.

       물리 계수(minForce/maxForce)는 BowlingBall에 그대로 남음.
   개선:
     - BowlingRuleConfig 또는 별도 LanePhysicsConfig ScriptableObject로 통합.
     - 레인 너비 / 거터 경계 / 발사 위치는 1개 source of truth로.

  5. 잠재적 버그 / 안정성

[P1] 이벤트 구독 중복 위험
--------------------------------------------------------------------------------
   위치: GameStateManager.EnterState(Ready) — OnConfirmPressed += OnReadyConfirm
   문제:
     - Ready 상태에 두 번 진입하면 같은 핸들러가 2회 구독될 수 있음.
     - C# 이벤트는 동일 핸들러 다중 구독을 허용하므로 호출 1회당 N회 발생.
   개선:
     - 구독 전 -=로 명시적 해제 후 구독.
     - 또는 Ready 상태가 1회 진입이라는 invariant를 명문화.

[P1] BowlingBall.powerGauge null 가능성
--------------------------------------------------------------------------------
   위치: BowlingBall.Start() — FindFirstObjectByType<PowerGaugeUI>
   문제:
     - PowerGaugeUI가 씬에 없거나 Start 시점에 비활성화 깊이 문제 시 null.
     - ExecuteLaunch()에서 powerGauge.ConfirmedNormalized 접근 → NRE.
   개선:
     - Inspector 강제 참조 + RequireComponent 또는 명시적 null 체크 후 fallback.

[P2] DebugResetController가 코루틴 정리에 StopAllCoroutines 사용
--------------------------------------------------------------------------------
   위치: DebugResetController.StopDanglingCoroutines()
   문제:
     - bowlingBall.StopAllCoroutines() / gsm.StopAllCoroutines()는 향후 추가될
       다른 코루틴까지 모두 중단시킴 → 의도치 않은 부수 효과.
   개선:
     - WaitUntilStopped와 TempScoringDelay 코루틴 핸들(Coroutine 변수)을
       각 컴포넌트에서 보관하고, 필요 시 개별 StopCoroutine으로 정리.
