  catastrophic 케이스고, 지금 남은 "간혹 위치가 살짝 어긋남" 은 다른 원인일
  가능성이 높습니다.

  호출 체인 정리

  가설 (가능성 순)

  가설 1 — BallAimer.Update 가 Y/Z 를 덮어쓰면서 spawnPoint 와 어긋남 (가장 
  유력)

  BallAimer.cs:36 의 한 줄:
  transform.position = new Vector3(x, transform.position.y, ballStartZ);

  - Z 는 ballStartZ = 0.5f 로 강제 고정 (인스펙터 값)
  - Y 는 transform.position.y 차용 — 즉, "그 순간 transform 의 Y"

  ResetToStartPosition 의 내부 검증은 ResetBall 직후 동기적으로 통과합니다.
  하지만 그 검증이 통과한 다음 프레임 Update 에서 BallAimer 가 Y/Z 를 위 코드로
  다시 씁니다.

  문제: 만약 spawnPoint.position.z ≠ 0.5f 이면 매 리셋마다 항상 Z 가 0.5 로
  스냅됩니다 — "정확한 위치" 와 다른 위치로 가는 결정적 원인. 또
  spawnPoint.position.y 와 ballStartZ 가 인스펙터에서 다르게 설정돼 있으면 매번
  같은 양만큼 어긋남. "간혹가다" 라기보다 "항상 어긋난다" 에 가깝지만, 사용자가
  미세한 어긋남을 매번 인지하지 못해 "간혹" 으로 느낄 수 있음.

  검증 방법: spawnPoint 의 Transform 값과 BallAimer.ballStartZ 인스펙터 값을
  비교. 또 한 번의 리셋 직후 콘솔에서 transform.position 과 spawnPoint.position
  을 찍어 비교.

  가설 2 — Interpolation buffer 잔존 → 시각상 1~2 프레임 글라이드

  Rigidbody Interpolation 이 Interpolate 또는 Extrapolate 면, 매 visual frame 의
   transform 은 [이전 물리 step 위치, 현재 물리 step 위치] 사이를 보간한 값.
  ResetBall 의 6단계 (kinematic→transform 세팅→SyncTransforms→Sleep→dynamic) 가
  rb.position 을 정렬하더라도 interpolation 의 previousPosition 캐시까지 비우진 
  않습니다. 결과: 리셋 직후 첫 1~2 프레임 동안 transform 이 "이전 종착점(레인
  끝)" 에서 "spawnPoint" 로 시각상 슬라이드. 이 프레임 중에 BallAimer.Update 가
  발동되면 가설 1 에 의해 Y 가 중간값으로 락됩니다.

  검증 방법: BowlingBall 의 Rigidbody Interpolation 을 잠시 None 으로 바꿔
  테스트. 어긋남이 사라지면 이 가설이 주범.

  가설 3 — Catch-up FixedUpdate 가 ResetBall 의 isKinematic = false 와 BallAimer
   의 isKinematic = true 사이 윈도우에 끼어듦

  핀 충돌로 무거운 물리가 누적되면 Unity 가 frame catch-up 으로 한 Update 안에
  여러 FixedUpdate 를 몰아 실행합니다. ResetBall 마지막에 rb.isKinematic = false
   로 되돌리는데, 그 직후 BallAimer 가 다시 true 로 토글하기 전에 FixedUpdate 가
   1회라도 끼어들면 중력이 한 틱 적용되어 Y 가 살짝 떨어짐. 검증 라인
  (ValidateResetPosition) 은 ResetBall 내부에서 동기로 통과한 직후이므로 이
  떨어짐을 못 잡습니다.

  검증 방법: ResetBall 직후 → BallAimer Aim 시작 직후 양 시점에서
  transform.position 을 로그. Y 가 후자에서 미세하게 작으면 (예: 0.15 → 0.149)
  이 가설이 맞음.

  가설 4 — spawnPoint 의 부모 변화 / 씬 중복

  오늘 발견한 Assets/Game.unity vs Assets/Scenes/Game.unity 중복 (§14-10-6). 두
  씬에서 BallSpawnPoint 의 위치/parent 가 다르면, 어떤 씬이 활성인지에 따라
  다르게 동작. Build 흐름과 Editor 흐름이 다른 씬을 로드하니 "쇼트/풀 무관" 인데
   "간혹" 인 것과 일치. 다만 사용자는 Editor Play 모드에서 본 거라 양쪽 씬을 다
  본 게 아니라면 이 가설은 약함.

  가설 5 — BallAimer.HandleStateChanged 가 prev=Scoring 일 때 linearVelocity = 0
   만 호출, angular 미처리

  BallAimer.cs:48:
  if (rb != null) { rb.linearVelocity = Vector3.zero; rb.isKinematic = true; }

  angularVelocity 는 클리어 안 함. ResetBall 에서 angularVelocity 를 이미 0 으로
   만들었으니 보통 문제 없지만, 가설 3 의 catch-up 한 틱에서 핀과의 잔여 접촉이
  회전을 누적시키면 회전 → 위치 미세 변화 (구르며 살짝 이동) 의 시드가 됩니다.
  우선순위는 낮음.

  public void ResetBall(Vector3 position)
  {
      var savedInterp = rb.interpolation;
      rb.interpolation = RigidbodyInterpolation.None;   // 보간 버퍼 잠시 무력화

      if (!rb.isKinematic) { rb.linearVelocity = Vector3.zero;
  rb.angularVelocity = Vector3.zero; }
      rb.isKinematic = true;

      // transform + rb.position 양쪽 모두 세팅
      transform.position = position;
      transform.rotation = Quaternion.identity;
      rb.position = position;
      rb.rotation = Quaternion.identity;

      Physics.SyncTransforms();
      rb.Sleep();
      rb.isKinematic = false;

      Physics.SyncTransforms();        // 두 번째 sync (가설 3 mitigation)

      rb.interpolation = savedInterp;  // 복구
      hasLaunched = false;
  }

  C. ResetBall 후 BallAimer 가 곧바로 isKinematic 을 토글하지 않게 — ResetBall 
  이 끝났을 때 이미 kinematic 으로 종료

  그대로 kinematic 유지. 그러면 BallAimer 가 isKinematic 을 또 토글할 일도 없고,

  // rb.isKinematic = false;   ← 제거

  private void ExecuteLaunch()

      hasLaunched = true;
      if (rb.isKinematic) rb.isKinematic = false;   // 명시 전환
      // ...
  }

  D. 진단 로그 추가 (먼저 가설 확정)

  수정 전에 어느 가설이 맞는지 가리려면 — 한 번의 리셋 후 4개 시점의
